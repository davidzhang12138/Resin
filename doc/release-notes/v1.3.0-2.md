# Resin v1.3.0-2

## Changes

- Preserve Clash `fallback` priority instead of converting it into latency-based `urltest` selection.
- Respect fallback probe timeouts and expected HTTP status codes. A reachable HTTP 503 response no longer counts as a successful 407 probe.
- Add SOCKS5 landing-service probes and an optional multi-target quorum, so front-proxy health can check the actual landing path and tolerate a failed sample endpoint.
- Resolve cached detour groups against the current subscription after refresh, avoiding references to retired groups.
- Gate releases on subscription, outbound, topology, proxy, API and application tests.

## Configuration

Clash fallback groups accept `interval` in seconds, `timeout` in milliseconds and `expected-status` for HTTP probes. Resin also accepts the following extensions on a fallback group:

```yaml
proxy-groups:
  - name: landing-front
    type: fallback
    proxies: [main-front, backup-front]
    url: socks5://landing-a.example:1080
    probe-urls:
      - socks5://landing-a.example:1080
      - socks5://landing-b.example:1080
      - socks5://landing-c.example:1080
    probe-quorum: 2
    interval: 20
    timeout: 1000
```

Candidates retain subscription order. The first healthy main front wins even when a backup is faster; it is selected again after recovery. SOCKS5 probes verify the server's authentication-method handshake without transmitting credentials. With multiple probe URLs, the default quorum is all configured URLs; set an explicit quorum to tolerate failed sample landing nodes. Existing TCP connections still require clients to reconnect when their path fails.

## Upgrade Notes

- This update does not add a database migration.
- Refresh affected subscriptions after upgrading to apply fallback settings.
- The probe URL extensions above are specific to Resin; ordinary HTTP/HTTPS Clash fallback configurations continue to work.
